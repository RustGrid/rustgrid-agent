# rustgrid-agent v1.4.8

This release prevents a hosted execution retry from replaying an AI request
registration failure from an earlier execution attempt or worker session, and
keeps confirmed pre-provider failures from consuming the active phase budget.

## Install or upgrade

On macOS with Homebrew:

```sh
brew update
brew upgrade RustGrid/tap/rustgrid-agent
```

For a new installation:

```sh
brew install RustGrid/tap/rustgrid-agent
```

## Changed

- Scope hosted AI request idempotency to the execution ID, execution attempt,
  worker session, and semantic call index. Retries within one semantic call
  remain stable, while a later execution attempt cannot replay a failed
  registration from an earlier session.

## Fixed

- Restore the worker's phase ledger when RustGrid explicitly confirms that an
  AI request failed before provider dispatch and did not consume call budget.
- Retry registration only when RustGrid marks the failure retryable, preserving
  the notebook and active phase across the bounded retry.
- Report RustGrid gateway status, upstream provider status, failure stage,
  provider contact, budget consumption, and reservation reconciliation as
  separate safe diagnostics.
- Surface legacy `409 ai_provider_request_failed` replays as
  `ai_request_idempotency_conflict` instead of treating them as provider
  failures.

## Compatibility and deployment

Before pinning canonical hosted workflows to v1.4.8, deploy the matching
RustGrid backend change from commit `deed7d4`:

- default new hosted executions to 40 model calls;
- persist requested and resolved budget provenance;
- emit the canonical signed manifest-v4 budget contract;
- return explicit registration failure details that distinguish provider
  contact, budget consumption, and reservation reconciliation.

The canonical workflow must continue accepting only `execution_id` and
`dispatch_nonce`. The selected budget remains authenticated manifest policy,
not an unsigned workflow input.

Artifact publication does not deploy the RustGrid backend, AgentOps, or
canonical workflow changes.

## Rollback

If rollback is required, stop new hosted dispatches and return canonical
workflows to `v1.4.7`. Do not replace or mutate existing tags or release
assets.
